1Executive summary

This project is a parameterizable mesh network-on-chip (NoC) router, written in SystemVerilog and built over eight milestones. It starts as one combinational router and ends as a two-stage, virtual-channel router that carries a coherence-style protocol without deadlock and refuses to be hurt by one compromised tile. Every claim in this report was measured, and every measurement can be rerun with one command.

1.1What was built

A router connects one compute tile to its four mesh neighbors. A grid of them moves messages between tiles. The project grew that router in eight steps, each one a self-contained folder with its own design, testbenches, tools and write-up:

MilestoneWhat it added

M2A 3×3 mesh of M1 routers, with multi-hop routing verified corner to corner
M3Credit-based flow control and per-input buffers, so every hop takes a bounded, registered cycle
M4Randomized-traffic verification, a latency and throughput sweep, and an analytic model that explains the results
M5Virtual channels with a two-pass allocator, and virtual networks that remove protocol deadlock
M6Security at the tile boundary: source stamping, a virtual-network guard, and a starvation watchdog
M7Synthesis on a real cell library, two timing fixes, formal proofs, and lint
M8A two-stage pipelined router, whole-mesh timing, a decision rule for which router to build, and a 4×4 mesh study

A ninth deliverable, the NoC Mesh Replay, is an interactive page that plays back real RTL simulations cycle by cycle, so the behavior described here can be watched as well as read.

1.3What the evidence rests on

A result is only as good as the checks behind it. The project layers several independent ones, so that no single checker has to be trusted:

  • Self-checking tests. Every testbench prints PASS or FAIL. The final router has 28 directed tests, plus randomized scoreboards that account for every packet.
  • Invariants checked every cycle in every router: credit conservation, buffer bounds, virtual-network isolation, arbiter fairness, and "no flit leaves through an edge port".
  • Equivalence runs. Each new milestone, configured as the old one, must reproduce the old results digit for digit (288 runs for the security layer; 80 sweep points for the VC router).
  • Mutation testing. Eleven realistic bugs are planted one at a time, in both pipeline modes. Every one must be caught, so a passing run means the checkers can fail.
  • Formal proofs for all inputs within the bound, with four planted-bug negative controls that must each make a proof fail.
  • Analytic models. Throughput must stay under a channel-load bound and latency must match a hop-count model.

The final regression runs all of it: 18 of 18 steps pass, in about 49 minutes (Chapter 7).

1.4Status, and what is not covered

The prototype is complete and verified. The design is a research and portfolio artifact, not a product, and it has deliberate limits:

  • Packets are a single flit. Multi-flit wormhole packets were left out on purpose.
  • Timing comes from pre-layout synthesis at one corner. It is sound for comparing designs and is not a sign-off frequency.
  • Traffic is synthetic. There are no real workload traces.
  • Security covers one compromised tile. Rate limiting against floods and timing side channels are out of scope, and the watchdog assumes a deadlock-free protocol (the virtual networks provide it).

Chapter 10 lists these with their consequences, and proposes the follow-on work, including the hardware and micro-architecture specifications this report is meant to lead into.

2Motivation and scope

2.1The problem: moving messages on a chip

A modern processor is no longer one core and a memory. It is dozens of agents: cores, cache slices, memory controllers, I/O blocks and accelerators. They all need to talk to each other, and the traffic between them decides how fast the whole chip runs.

A single shared bus cannot carry that traffic. Only one agent can speak at a time, and the wires get longer and slower as agents are added. The standard answer is a network-on-chip: each agent attaches to a small router, routers connect to their neighbors, and a message hops from router to router until it arrives. The usual layout for large chips is a two-dimensional mesh, because it is regular, it maps naturally onto a floorplan, and its wires are all short.

The router is the building block, and its design decides three things about the whole network:

  • How much traffic it carries (bandwidth) and how quickly (latency).
  • Whether it works at all, because a network that can deadlock under the wrong traffic mix is broken no matter how fast it is.
  • What it costs in area and in clock frequency, since the router sits on the critical path between every pair of agents.

2.2Why this project

The project has one technical aim and one practical one.

Technical aim. Build a real router the way a design team would, and answer four questions with evidence rather than opinion:

  1. Performance. Where does a simple router lose bandwidth, and what fixes it?
  2. Correctness. What breaks when different message types share buffers, and what prevents it?
  3. Trust. What can a single misbehaving agent do to everyone else on a shared fabric, and how is that stopped at the cheapest possible point?
  4. Implementation. What does each feature cost in silicon area and clock period, and which router should a given chip actually build?

Practical aim. Produce a complete RTL design and verification portfolio piece: a design with a specification, an architecture that evolves for stated reasons, a layered verification environment, synthesis and formal results, and honest documentation of what worked, what failed and what was corrected.

2.4Scope

In scope

  • A 5-port mesh router with XY routing, in SystemVerilog, for mesh sizes up to 16×16 (4-bit coordinates)
  • Credit-based flow control, virtual channels, virtual networks, a two-pass allocator, an optional second pipeline stage
  • A three-class coherence-style traffic model (request, snoop, response)
  • Defenses at the tile port against one compromised tile
  • Synthesis on sky130, formal proofs, lint, mutation testing, analytic checks
  • A replay visualizer for the final design

Out of scope, on purpose

  • Multi-flit wormhole packets (head, body, tail handling)
  • Adaptive routing, non-mesh topologies
  • Placement, routing, and sign-off timing
  • Real workload traces; only synthetic patterns
  • Rate limiting, confidentiality and side-channel defenses
  • A full coherence protocol; the protocol model only has to create the dependency chain that causes deadlock

Keeping packets to a single flit is the largest simplification. It keeps the router small enough to verify completely, and every result in this report is stated for that case. Chapter 10 describes what multi-flit packets would add.

2.5How "done" was decided

The project follows four rules about when a milestone is finished:

  1. Its own regression passes, and the script exits with an error if any step does not print its pass line.
  2. Every claim in its write-up is backed by a command that reproduces it.
  3. If it changes an earlier design, it is configured to behave as that design and must reproduce the earlier results exactly.
  4. Any defect found in an earlier result is corrected openly, in the earlier document, not only the later one.

Rule 4 was used. M8 found that M7's timing method overstated its fixes by about a factor of two, and M7's write-up now carries a correction note at the top (Chapter 9).

3Background: how a NoC router works

This chapter explains the ideas the rest of the report relies on. A reader who already knows routers, credits and virtual channels can skip to Chapter 4.

3.1Packets and flits

Agents exchange packets. On the wire a packet is cut into flits (flow-control units), one of which crosses a link per clock cycle. In this project every packet is exactly one flit, so the two words mean the same thing here. The final design uses a 34-bit flit:

3.2Routing

Each router decides, from the destination coordinates and its own, which of its five ports a flit leaves on. The project uses XY dimension-order routing: move along X until the column matches, then along Y until the row matches, then deliver to the local tile.

The rule is not a style choice. A packet never turns from Y back to X, so waiting dependencies between packets can never form a cycle through the routing function. XY routing is deadlock-free on a mesh by construction. This matters later, because it separates two different kinds of deadlock: the one routing prevents, and the one it cannot (Section 3.6).

3.3Arbitration

Several inputs may want the same output in the same cycle, and one output carries one flit per cycle. A round-robin arbiter picks the winner: it remembers who won last and gives the next requester priority, so no input is starved. One arbiter sits at each output, and fairness is a checked property, not an assumption (a requester that keeps asking is granted within a bounded number of cycles, which Chapter 7 proves formally).

3.4Flow control: handshakes and credits

A flit may only be sent if the receiver has room for it. M1 and M2 use a valid/ready handshake: the receiver says "ready" each cycle. That forces a combinational path from every receiver back to every sender, so one clock cycle spans the whole mesh and the design could not run at any useful frequency.

From M3 on the project uses credit-based flow control, which is what real on-chip networks use. The sender keeps a counter of free slots in the receiver's buffer. Sending costs one credit; the receiver returns a credit when it frees a slot. Nothing is combinational across a hop.

3.5Head-of-line blocking and virtual channels

With one FIFO per input port, only the flit at the head can request an output. If its output is busy, every flit behind it waits, including flits bound for idle outputs. This is head-of-line (HOL) blocking. Deeper buffers hold more waiting flits but do not let any of them jump the queue, so they barely help (Chapter 5 measures +7% for doubling the depth).

A virtual channel (VC) splits an input's buffer into several independent FIFOs that share the one physical link. A small vc field on each flit names which FIFO at the far end it goes into, and credits are counted per VC. A blocked flit now blocks only its own VC.

Adding VCs adds two decisions per hop. VC allocation picks which VC at the next router a flit will use. Switch allocation matches waiting flits to output ports each cycle. A single-pass allocator throws most of the new choices away, which is why M5 also adds an optional second pass (Section 5.5).

3.6Message classes and protocol deadlock

Routing deadlock (a ring of packets each waiting for a buffer the next holds) is prevented by XY routing. A different problem remains: protocol deadlock, which comes from dependencies between message types, not from paths.

A coherence transaction is a chain of three messages. A requester sends a request (REQ) to the line's home. The home sends a snoop (SNP) to the current owner. The owner sends a response (RSP) to the requester. Each endpoint has finite space, so each follows a rule: a home accepts a REQ only if it has room to queue the SNP it now owes, and an owner accepts a SNP only if it has room to queue the RSP. A requester always accepts an RSP.

The fix is a virtual network (VN): a group of VCs reserved for one message class, so one class's backlog can never fill the buffers another class needs. With one VN per class the argument runs backward from the end of the chain: RSPs always drain, so SNPs always drain, so REQs always drain.

3.7Threat model for a shared fabric

The network connects agents that may not trust each other. The project's model is deliberately narrow: one tile is compromised. It can inject any flit, with any header fields, on any VC, as fast as its credits allow, and it can refuse to consume what is delivered to it. The routers, the links between them and all other tiles are trusted. Chapter 5.6 states the goals (authenticity, isolation, availability), the three attacks and the defenses, which all sit at the one place where a tile meets the network: the router's local port.

3.8How performance and cost are measured

3.9Simulation, formal verification and mutation testing

These are three different kinds of evidence, and the project uses all three.

  • Simulation checks properties on the traffic that happened to run. It is fast and scales to whole meshes, but it can only find bugs its stimulus reaches.
  • Formal verification searches every possible input sequence for a counterexample and either finds one or proves there is none (within a stated bound, or for all time when proved by induction). It is exhaustive but works on small pieces: an arbiter, or one router with its neighbors modeled as assumptions.
  • Mutation testing checks the checkers. It plants a realistic bug, reruns the tests, and requires them to fail. A test suite that passes on buggy hardware is not evidence of anything.

4Approach and methodology

4.1Building in milestones

The router was not designed once and then verified. It was grown in eight steps, each answering one question raised by the last, with a complete verification pass before the next began. Each step lives in its own folder with its own design, testbenches, tools, results, run.sh and README, and copies the previous step's files rather than rewriting them. That makes every milestone a demonstrable artifact on its own, and makes every comparison between two designs a comparison between two folders.

4.2Working principles

Five rules were applied throughout. They explain why the project's results can be trusted, and several of the corrections in Chapter 9 came from applying them.

PrincipleIn practice
Measure, do not assertEvery performance, area and timing statement comes from a sweep or a synthesis run whose data is in a CSV. Where a model predicts a result (channel load, hop-count latency), the measurement is checked against it, and the cases where they disagree are investigated, not hidden.
A refactor must prove it changed nothingConfigured as the old design, the new design must reproduce the old results digit for digit. M5 reproduces all 80 of M4's sweep points. M6 reproduces 288 earlier runs. M7 and M8 do the same after timing changes. This pins behavior, not just correctness.
Verify the verificationMutation testing plants known bugs and requires the checkers to catch every one. Formal proofs carry negative controls: a planted bug must make each proof fail.
Show the attack succeed firstA defense is only evidence if the attack works without it. Every security result is paired with the same attack against the unprotected router, and a passing run requires both directions.
Correct the record openlyWhen a later milestone showed an earlier number was wrong, the earlier document was edited with a dated correction. Nothing was quietly replaced.

4.4Conventions

  • Self-checking testbenches. Every testbench prints PASS or FAIL and sets a result line the scripts can match. No waveform viewer is needed to know whether a milestone works, though a VCD is written when a testbench runs directly.
  • Scripts that fail loudly. vvp exits with status 0 even when a testbench prints FAIL, so every run.sh requires each step's own pass line and exits non-zero otherwise. This was added to M1 to M4 late and verified by planting a bug.
  • Verification code stays out of synthesis. Embedded checkers, counters and configuration checks are wrapped in `ifndef SYNTHESIS, so synthesis sees exactly the hardware and simulation keeps every check.
  • One README and one folder per milestone, with ASCII or SVG diagrams, so each milestone can be read and run without the others.
  • Generated files are not source. Compiled simulations, waveforms and proof run directories are regenerated by the scripts and are excluded by .gitignore.

5The milestones

This chapter follows the project in order. Each section states the question the milestone answers, what was built, how it was verified, and what it found. The later milestones (M5 to M8) carry the main results and are correspondingly longer.

5.1M1: a single router

Objective

Build one correct 5-port router in isolation, before any network exists, and prove it makes the right decision for every kind of packet.

Design

  • Ports. North, south, east, west and local, numbered 0 to 4. Each has an independent input half and output half.
  • Packet. One 16-bit flit: 4-bit destination X, 4-bit destination Y, 8-bit payload.
  • Routing. XY dimension-order routing (Figure 3.2), computed from the flit's destination and the router's own coordinates.
  • Arbitration. A round-robin arbiter per output port (rr_arbiter.sv), reusable and later carried through every milestone.
  • Flow control. A valid/ready handshake on every port. The router stores nothing, so a flit that loses arbitration must be held by its sender.
  • Timing. Purely combinational from input port to output port.

Verification

A self-checking directed testbench drives one router, parked at mesh position (1,1), through nine packets and 13 checks:

ScenarioWhat it proves
Straight through, W→E and N→SA packet that still needs to move in the dimension it arrived from passes straight through
Turn, E→S and W→NA packet whose X is already correct turns to fix Y

Findings

The main surprise was the simulator, not the design. Three constructs that are ordinary SystemVerilog crashed or silently misbehaved in this Icarus build: a for loop reading a packed-struct field inside always_comb; a nested loop comparing two loop-indexed array reads; and an output port declared as an unpacked array of structs, which read as x from outside the module. The router uses generate loops and packed arrays instead. Each workaround produces the same hardware as the plain loop. This set the rule for the whole project: write the subset that every tool agrees on.

5.2M2: a full mesh

Objective

Show that routers compose: that XY routing, hop by hop, delivers packets across a grid, including turns and contention between packets arriving from different directions.

Design

M2 changes no router logic. Ports on the mesh boundary are tied off: inputs never valid, outputs always ready. Each router's local port is exposed as an array indexed by tile number (y × width + x).

5.3M3: credit-based flow control

Objective

Replace the valid/ready handshake with the mechanism real interconnects use, so a hop becomes a real, bounded, registered clock cycle.

Design

  • A FIFO per input port (flit_fifo.sv), a circular buffer of BUFFER_DEPTH slots (default 4). A flit is pushed the cycle it arrives and popped the cycle it is forwarded.
  • A credit counter per output port, reset to the receiver's buffer depth. A request for an output is only formed if its credit count is above zero, so an output with no credit never appears as a candidate in arbitration at all.
  • Credit return. Each pop from an input FIFO sends a single-cycle credit_return pulse upstream, replacing the old ready wire (Figure 3.3).
  • Routing and arbitration are unchanged from M1 and M2; they now act on the flit at the head of each FIFO.

Verification

The FIFO has its own unit test first (ordering, full and empty, wraparound, simultaneous push and pop), because bugs are cheaper to find before it is wired in. The router testbench then reruns M1's scenarios on the buffered datapath and adds the scenarios this milestone exists for. It models both ends of a link as real credit-aware parties: the sender refuses to send at zero credits, and the downstream neighbor is an actual bounded FIFO, so credit conservation is enforced by the simulation, not merely asserted.

Findings

Lesson: cut-through means "check now, then wait"

The hardest bug of the milestone was in the testbench's sense of time. This router is cut-through: a flit pushed into an empty FIFO with credit can be routed, arbitrated and appear on an output in the very cycle it arrives. A polling loop that always waits for the next clock edge before checking misses that first cycle, and every later check ends up one flit out of phase, which looked exactly like a routing or ordering bug. The fix was to check first and wait only if nothing has happened yet.

5.4M4: real verification

Objective

Verify the credit-based mesh under sustained load, measure how much load it carries, explain the measurement with a model, and verify the verification itself.

Design and environment

  • mesh_credit.sv applies M2's wiring to M3's router. Unlike M2's mesh it has real per-hop latency: a four-hop corner-to-corner packet takes exactly four cycles.
  • Randomized scoreboard (random_traffic_tb.sv): every tile injects at a fixed rate for thousands of cycles over four traffic patterns, and every packet must arrive exactly once, in order relative to other packets from the same source, with unchanged data.
  • Embedded invariants in the RTL, checked every cycle in every router: FIFO occupancy never exceeds capacity, credit counters never exceed buffer depth, and no input with a ready flit waits more than the round-robin bound for arbitration. Each violation increments a global counter, and every testbench fails if it is nonzero, so a fired assertion cannot scroll past in an otherwise-passing log.
  • Open-loop sweep (latency_sweep_tb.sv): the standard method (Section 3.8), 4 patterns at 20 offered loads, 80 points, each also a full correctness run including a drain-after-load deadlock check.

Findings

A real bug, and where it was

Hotspot traffic first produced scoreboard failures that looked exactly like a router data-integrity bug. Chasing it took five steps, each ruling something out.

  1. The scoreboard's 4-bit sequence tag could wrap onto a still-outstanding packet when one packet waited 50 or more cycles under congestion. That was a real but false mismatch, fixed by tracking which tag values are in use. The failure persisted, so it was not the tag.
  2. Tracing the sending router's FIFO and credit state cycle by cycle showed the testbench's sender-side credit counter believed it had room when the real FIFO was already full, so a push was silently dropped.
  3. The root cause: the testbench updated the counter in two separate always-blocks, one on send and one on credit return. Under the densest injection of any milestone so far, a send and a same-cycle credit return occasionally collided and one update was lost, leaking exactly one credit.
  4. The fix collapsed both updates into one synchronous process covering sent, returned, both and neither, exactly as the router's own counter does.

The RTL was correct the whole time. A testbench that tracks protocol state needs the same care against races as the design it tests.

This Icarus build also cannot parse concurrent assertions (property and assert property), so credit conservation and starvation freedom are implemented as immediate assertions plus a procedural bounded-wait counter. M7 later proves the same properties formally.

5.5M5: virtual channels and virtual networks

Objective

M4 found that uniform traffic saturates at 75% of what the wiring allows, and that deeper buffers barely help. M5 removes head-of-line blocking with virtual channels, then uses the same mechanism to remove a second, nastier problem that M4's traffic could not show: protocol deadlock.

Design

  • Virtual channels. Each input port has NUM_VNS × VCS_PER_VN independent FIFOs, numbered vc = vn × VCS_PER_VN + k. A vc field travels with every flit and picks the FIFO at the far end. Credits are counted per VC, with one counter per output VC and one credit wire per VC.
  • Eligibility. A head flit is eligible if its output port has a free slot in at least one VC of the flit's own virtual network.
  • Switch allocation is separable and input-first: each input picks one eligible VC (round-robin), then each output picks one requesting input (round-robin). With SA_ITERS=2 a second pass repeats both stages for the inputs and outputs the first pass left unmatched. Pass 2 scans in the same order but never moves a round-robin pointer; only pass-1 wins rotate them (the rule from iSLIP, McKeown 1999), so pass 1's fairness bounds still hold.
  • VC allocation comes after switch allocation, which is legal because packets are single flits and eligibility already guaranteed a free VC. The output VC is chosen round-robin among the VCs of the flit's network that have credit.
  • Virtual networks. A flit never leaves its network. The class field in the flit (noc_pkg.sv adds message class and sender coordinates here) decides which VN it lives in.
  • Everything still happens in one cycle per hop. A new input to the second round-robin arbiter, req_b, shares the priority pointer without moving it, which is how pass 2 is built.

Configured as 1 VN × 1 VC, the new router is behaviorally identical to M4's. The equivalence check proves it (below).

5.6M6: fabric security

Objective

Show what a single compromised tile can do to a shared fabric, demonstrate each attack succeeding against M5's router, then stop it with the smallest possible hardware at the one place it can be stopped.

Threat model

  • The attacker controls one tile (a compromised accelerator, malicious firmware, a buggy agent). It can inject any flit with any header fields on any VC as fast as its credits allow, and it can refuse to consume what is sent to it.
  • Trusted: the routers, the links between them, and the other tiles.
  • Goals. Authenticity: a tile cannot claim to be another tile. Isolation: a tile cannot break the guarantees the network gives everyone else (M5's deadlock freedom). Availability: one tile cannot freeze traffic between other tiles.
  • Out of scope. Physical attacks or a malicious router; a tile refusing to serve requests (a protocol-level problem needing timeouts); volumetric flooding (rate limiting); confidentiality and timing side channels.

The trust boundary

Every defense sits at each router's local port, where a tile meets the network. Links between routers stay trusted. That split changes what an assertion means: on a link, a flit in the wrong network can only come from a broken router upstream, so it is an RTL bug and an assertion; at the local port the same flit is an attack, so the router refuses it and raises an alarm. All of it is behind one parameter, SECURE; SECURE=0 builds M5's behavior, the vulnerable baseline every attack is shown against.

Attack 1: source spoofing

Setup. Homes enforce an access-control list: a protected transaction may only be served for a trusted tile (the top row), and the home reads the requester's identity from the flit's source field.

Attack. The attacker at tile (2,2) sends protected requests with the source field set to (0,0), a trusted tile. Against M5's router every forged request is served, and the impersonated tile is hit with responses it never asked for. This is the on-chip version of a reflection attack: the attacker cannot read the data, but it can make the system act for it and dump the results on someone else.

Defense. The router overwrites the source field with its own coordinates on every flit entering from the tile. A tile may claim anything; the network reports where the flit really came from. This is ingress filtering in the manner of BCP 38, done in hardware at the only place it can be, and it is the principle behind hardware-assigned initiator identities in real SoC fabrics.

Attack 2: virtual-network hopping

M5's deadlock argument assumes the response network holds only responses. The attack: a greedy tile notices the response network is less congested and puts its requests there. A REQ can now sit at the head of a home's RSP buffer, waiting for room to queue a SNP, and every RSP behind it waits too. Against M5's router this deadlocks the whole fabric in every run, at a load where the networks never deadlocked before. One misbehaving tile takes the guarantee away from everyone.

Attack 3: black hole

The attack. The attacking tile simply stops consuming what is delivered to it. Its ejection credits never return, so flits addressed to it wait in its router's buffers; the flits behind them, addressed to anyone, wait too because of head-of-line blocking; and the routers feeding those buffers back up the same way. The backpressure spreads (tree saturation) until traffic between tiles that have nothing to do with the attacker is frozen. A corner tile does it as thoroughly as the center.

Defense. Per virtual network, the local ejection port runs a watchdog. It counts consecutive cycles in which a flit is waiting for the tile and the tile has returned no credit. After WD_LIMIT cycles it quarantines that network: its flits still win the switch but are discarded instead of sent, which drains the router's buffers and unwinds the backpressure. The moment the tile returns any credit, quarantine lifts. A slow but live tile never trips it, because any credit resets the count, and the discarded flits were addressed to the tile that refused them.

Hardware cost

All of it sits at one port per router. Source stamping turns the 8 source bits into constants. The network guard is a 2-bit compare per local VC gating the FIFO push. The watchdog is, per network, a counter of log2(limit+1) bits (9 bits at 256), a quarantine flop and an override on that network's credit check. Section 5.7 measures it: the secure router is smaller than the unprotected one.

5.7M7: synthesis, timing and formal verification

Correction carried by M7's own write-up

M7 synthesized one router alone and reported its longest path as the critical path. M8 later showed this overstated the timing fixes by about a factor of two (Section 5.8). The behavioral claims (equivalence, formal, mutation) are unaffected. This section reports M7's findings with the corrected whole-mesh timing, and M7's original single-router table is kept, labeled, in Appendix B.

Objective

M1 to M6 lived entirely in simulation. M7 puts the design through the tools an RTL team ships with: synthesis onto a real cell library, formal verification, and lint. It asks what each feature costs in silicon, and fixes what synthesis finds.

Setup

  • Synthesis: Yosys 0.69 with the slang SystemVerilog frontend, mapped to SkyWater sky130_fd_sc_hd at the typical corner (25 °C, 1.8 V), with ABC static timing. Everything simulation-only is wrapped in `ifndef SYNTHESIS, so synthesis sees exactly the hardware.
  • Formal: SymbiYosys, with arbiter properties proved by k-induction and the router's credit protocol by bounded model checking.
  • Lint: Verilator 5.032 with -Wall, on two views (synthesizable, and with checkers) across several configurations, with zero warnings required.

What synthesis showed

Finding 1: buffers are the router

63 to 71% of a router's area is flip-flops, almost all of it FIFO storage (5 ports × VCs × depth × 37 bits). Doubling the storage roughly doubles the router. In whole-mesh numbers a single 4-flit queue per input is 25,612 µm² per router and an 8-flit queue is 47,175.

Finding 2: in a single-cycle router, VCs do not pay per nanosecond

The allocator lengthens the critical path faster than it raises throughput per cycle. On the whole mesh, four VCs with one pass cost +56% in clock period (3.95 to 6.16 ns) for +9% throughput per cycle; the second pass costs another +41% (to 8.66 ns) for another +10%. In flits per node per nanosecond, M5's best router delivers about half of the simple router's. Real VC routers pipeline allocation for this reason, which is what M8 does.

Finding 3: security costs no area

The secure router is smaller than the unprotected one: 3.4% smaller in M7's single-router run and 3.7% smaller in M8's whole-mesh run (58,078 to 55,903 µm² per router, same configuration). Source stamping turns the local port's 8 source bits into constants, so synthesis removes those flops from every local-port buffer slot. That more than pays for the watchdog counters. The other checks sit on the push path and in eligibility logic, off the critical path.

Two timing fixes

The first synthesis run reported every critical path the same way: starting at an input FIFO's read pointer and running through the router in one cycle, through the read mux, route compute, eligibility, both arbiter stages (twice with two passes), the VC mux and the crossbar. Two pieces of that path were doing work that did not need to be there.

On the whole mesh the two fixes cut the critical path 17% for the simple router (4.95 to 4.13 ns) and 13% for the VC router (10.10 to 8.79 ns). None of it changed behavior, and that is proved: all 288 honest-traffic runs reproduce M4's and M5's results digit for digit; all 56 attack runs reproduce M6's line for line; and the new arbiter is formally equivalent to the old one (next).

5.8M8: pipelining, and which router to build

Objective

M7 found that a single-cycle VC router loses per nanosecond to the simple router, and named the fix: split the hop into stages. M8 builds it, re-measures timing honestly, and turns the data into a decision rule.

The two-stage router

A PIPE parameter selects the hop structure. PIPE=0 builds M7's router unchanged, and the equivalence check confirms it still reproduces M4's and M5's results exactly.

  • Every state update happens in stage 1: the pop (and credit return upstream), the output VC's credit charge, and the arbiter pointers. So each allocation sees exactly the state the previous one left. There is no stale-request hazard and no replay logic, which is why the change stays small and verifiable.
  • A longer credit loop. A credit comes back three cycles after its flit was allocated, not two. A single VC with 2-deep buffers can then use only two thirds of a link. Directed test T6 caught exactly this (below).
  • The watchdog's discard flag travels with its flit, so the black-hole defense still identifies every discarded flit in both modes.

Measuring timing honestly

A hop does not end at a router's output port. It ends in the next router's input buffer, in the same clock cycle. Synthesized alone, a router's ports are free endpoints and that cross-link path is cut in half. M8's synthesis script flattens the whole 3×3 mesh, so the only endpoints are the tiles' ports, and reports where the critical path starts and ends. The single-cycle routers' paths now visibly cross a link: they start in one router (a FIFO head or a credit counter) and end in a neighbor's input logic.

6.4Operation, step by step

The RTL is organized as numbered steps. In PIPE=0 everything from step 1 to step 6 happens in one clock cycle, and a flit allocated in a cycle appears at the neighbor's FIFO at the next clock edge.

Step 0: write into a VC FIFO

A flit is pushed into the FIFO that its link-level vc names. On the local port with SECURE=1 two rules apply first (Section 6.7). The XY route is computed here, once per input port from the destination and the router's own coordinates, and stored in a 3-bit tag beside the flit. Storage is 37 bits per slot (34 flit bits and the tag).

Step 1: read the route

At the head of each FIFO the route is simply read from the tag. This is route-at-write (M7): the same decision in the same cycle, with one comparator per port in place of one per VC.

Step 2: eligibility

Input VC I requests output o if its FIFO is not empty, its route tag selects o, and output o has at least one free slot in some VC of the flit's own network. A flit's network is simply which VC it sits in; the isolation checks keep that true.

Step 3: switch allocation

  1. Pass 1, input stage. Each input port nominates one eligible VC, chosen round-robin over its VCs.
  2. Pass 1, output stage. Each output grants one of the input ports whose nominee wants it, round-robin. Only pass-1 wins rotate the round-robin pointers.
  3. Pass 2 (SA_ITERS=2). Inputs and outputs left unmatched repeat both stages, using the second request port of the same arbiters. This pass never moves a pointer.

Step 4: datapath

Each input port has exactly one crossbar input. Its VC mux selects the VC that won in pass 1 or pass 2, and that VC pops. Each output then takes the flit of the input it granted. One flit per input per cycle is therefore a property of the wiring and not only of the allocator, and the structure is cheaper than a flat (ports × VCs)-to-1 mux per output, which would need about twice the mux inputs at four VCs.

Step 5: VC allocation

Each sending output gives its flit an output VC: round-robin among the VCs of the flit's network that hold credit. Eligibility already guaranteed one exists, so VC allocation can safely come after switch allocation (it could not if packets had several flits).

Step 6: where the hop ends

With PIPE=0 the crossbar and output port use the signals directly. With PIPE=1 stage 1 ends in a register holding, per output, the flit, the crossbar select and the output VC (plus a valid bit and the watchdog's discard flag), and stage 2 runs the crossbar and link from those registers. The pop, the credit return upstream, the credit charge and the arbiter updates all happen in stage 1.

6.5Flow control

  • Per output VC, a counter initialized to BUFFER_DEPTH. A send decrements it; a credit_return pulse on that VC's wire increments it. The counter's width is log2(BUFFER_DEPTH+1) bits.
  • Invariant (checked every cycle, and proved for the whole router): credits held plus flits in flight plus free slots equal BUFFER_DEPTH. The counter never exceeds the depth, no router sends into a full buffer, and no router returns a credit it does not owe.
  • Credit loop length. In PIPE=0 a credit is back two cycles after its flit was allocated; in PIPE=1, three. A VC needs a buffer at least as deep as the loop to sustain full link rate, which is why a 2-deep single VC reaches only two thirds of a link in two-stage mode.
  • VN-level credit check. Eligibility asks whether any VC of the flit's network at the output has credit; the VC allocator then picks one that does.

6.6Fairness guarantees

Both bounds are exact consequences of the round-robin pointer rules, checked every cycle in every router, and proved for arbiters of every width the router uses:

  • Output stage: an input port that keeps requesting an output waits at most NUM_PORTS − 1 grants.
  • Input stage: an eligible VC sees at most NUM_VCS − 1 pass-1 wins by its sibling VCs.
  • Pass 2 cannot break either bound because it never moves a pointer.

6.7Local-port security

With SECURE=1, three mechanisms act at the local port and nowhere else:

MechanismBehavior
Source stampingOn the local input only, the flit's source fields are replaced by the router's own coordinates before the flit is stored. The tile's claimed source is discarded.
Network guardA local flit is accepted only into a VC of its class's network. Otherwise it is refused (alarm[0] pulses), nothing is stored, and the credit the tile spent is not returned.
Starvation watchdogPer network, a counter of consecutive cycles in which a flit waits for the local port and the network has no ejection credit. At WD_LIMIT the network is quarantined (alarm[1] is high): its flits still win the switch but are discarded, each pulsing alarm[2]. Any credit returned lifts quarantine immediately and resets the count.

Transit flits on router-to-router links are not stamped or guarded, because links are trusted. A wrong-network flit on a link is an RTL bug and fires an assertion. Assertions about link traffic apply only when SECURE is non-zero, since with SECURE=0 the local port is deliberately unchecked and the attack tests need the router to carry the attacker's flits.

6.8The mesh

vc_mesh instantiates one router per grid position with its coordinates, passes all parameters through, and connects neighbors with continuous assigns between constant slices (no runtime indexing, which this Icarus build mishandles). Vertical links join router (x,y)'s south port to (x,y+1)'s north port; horizontal links join east to west. It adds one invariant: a flit may never leave through an edge port, which would be a misroute.

6.9Implementation notes

  • Reset. Control state (FIFO pointers and counts, credit counters, arbiter priorities, watchdog counters and quarantine flags, pipeline valid bits) resets asynchronously, active low. Datapath storage (FIFO slots and tags, pipeline data registers) has no reset, because an empty buffer's contents never matter and non-reset flops are smaller.
  • Arbiter. A thermometer mask of positions at or above the priority pointer, granting the lowest set bit of requests AND mask, or the lowest set bit of requests if none (wrap-around); lowest set bit by x AND (NOT x + 1). Formally equivalent to M1's loop-based arbiter for 1 to 8 requesters.
  • Encoders. One-hot to binary conversions are flat generate-based encoders, not chained ORs, which Verilator flagged as false combinational loops.
  • Simulation-only code. All checkers, counters and configuration checks are behind `ifndef SYNTHESIS. Violations increment a global counter in the package, and every testbench fails if it is nonzero.
  • Lint and synthesis. Zero Verilator warnings on both views. The design synthesizes through Yosys with the slang frontend, flattened as a whole mesh for timing.
  • Simulator-driven style. Constant-indexed arrays and generate loops replace runtime array indexing, and package functions are called with explicit package scope inside generate blocks. Appendix E lists the quirks.

7.10What the verification does not establish

Stating the limits is part of the evidence.

  • Deadlock freedom is argued and measured, not proved by a tool. The argument is the backward chain of Section 5.5; the evidence is 48 protocol runs per configuration with zero deadlocks, a drain-after-load check on every sweep point, and the mutation that removes network isolation being caught. A temporal proof of deadlock freedom for the whole mesh was not attempted.
  • The whole-router formal proofs are bounded (12 cycles). They cover filling and draining every 2-deep buffer several times and any input sequence within that window, but they are not unbounded proofs of the credit protocol.
  • Traffic is synthetic. The patterns are standard and adversarial by construction, but no real workload trace was run.
  • Only one compromised tile is modeled, with a defined set of three attacks. A cleverer attack outside the threat model is not covered.
  • Single-flit packets. Every guarantee is stated for them. Multi-flit packets add per-VC state and new hazards that none of these checks exercises.
  • Pre-layout timing. Critical paths exclude wires, clock-to-q and setup, and one process corner.

8.3The four questions, answered

QuestionAnswer, with the evidence that carries it
Performance. Where does a simple router lose bandwidth, and what fixes it?It loses it to head-of-line blocking: uniform traffic saturates at 75% of what the wiring allows while the busiest channel is only 56% utilized, and doubling the buffers gains 7%. Four VCs with a two-pass allocator reach 0.905 at equal storage (+12% over one deep queue). Neither change works alone.
Correctness. What breaks when message types share buffers?The coherence protocol deadlocks, with no routing cycle involved: 8 of 8 runs at 16 outstanding transactions per tile, and three times the buffers only moves the cliff to 32. One virtual network per class removes it (0 of 48 runs), by the backward argument RSP, then SNP, then REQ.
Trust. What can one bad tile do, and where is it stopped?It can impersonate another tile (8 of 8 runs breached), deadlock the whole fabric by hopping networks (8 of 8), or freeze unrelated traffic by refusing deliveries (victims at 0.022 of the 0.178 they offer, with 128 flits stuck). Three small mechanisms at the local port stop all three with zero victim packets lost, change nothing for honest traffic across 288 runs, and cost no area.
Implementation. What does each feature cost, and what should be built?See the table above. At a clock under about 4 ns build the pipelined simple router (0.221 flits per node per ns); at about 8 ns or slower build the pipelined 4-VC two-pass router (+12 to +22% bandwidth). The coherence protocol needs virtual networks at any clock.

8.4Where the evidence is weakest

  • The decision rule between routers rests on pre-layout critical paths at one corner. Wire delay would lengthen the cross-link path and favor the pipelined designs, so the rule's direction is robust but its crossover clock periods are not sign-off numbers.
  • The recommendation at 5.35 to 7.94 ns is within noise (+2%) and is resolved on latency, not bandwidth.
  • The 4×4 study covers two router configurations and one traffic pattern for throughput. The protocol and security checks on 4×4 are single configurations.

9.2Tooling lessons

  • Windows line endings. Python wrote carriage returns in text mode, which blinded shell substitutions in the mutation script. Source files were normalized, and Python now writes with explicit newline control.
  • Paths with spaces. SymbiYosys cannot take spaces in file lists, so the proof scripts use relative paths from each proof's directory. It also exits non-zero on an expected FAIL, which broke scripts running with pipefail; the verdict is now read from the last "DONE" line.
  • Parallel synthesis. Running eight Yosys jobs at once crashed from memory pressure. The script uses three or four in parallel with a retry.
  • Result parsing. A flop-count parser missed numbers in scientific notation until it was fixed.
  • Bash heredocs and embedded Python. Escaping broke inline scripts repeatedly; analysis code lives in files.

9.3Cross-cutting lessons

  1. Verify the thing that decides the answer. Timing from one router, throughput from light-load tests, security from a defense never shown to fail: each looked fine and each was wrong or empty.
  2. Make every refactor prove it changed nothing. Equivalence against the previous milestone turned "I think it's the same" into 288 matching runs, and made later timing changes safe.
  3. Check the checkers. Mutation testing found a redundant mutant, a false-positive hazard and invisible-to-stimulus bugs. Negative controls did the same for the proofs.
  4. Predict, then measure. A model that says where each pattern must saturate turned one surprising result (uniform traffic) into a finding with a cause. Without the model it would have read as "about 75%".
  5. A testbench is a design. It needs the same care about timing and races as the RTL. The two worst debugging episodes were testbench bugs.
  6. Correct the record where the claim lives. M7's original document now opens with its correction.

9.4What would be done differently

  • Synthesize the whole mesh from the first synthesis milestone, and compare with the single-router number as a cross-check.
  • Put the log-gating wrapper in every run.sh from M1, instead of adding it at the end.
  • Build the replay checker before the replay page.
  • Keep one shared testbench library for the credit-tracking and scoreboard code, instead of carrying copies forward and fixing a race in each.

10.2Candidate next steps

Ordered roughly by how much each would change the design's real-world relevance per unit of work.

  1. Multi-flit wormhole packets. The largest gap between this design and one that could carry real traffic. New hazards appear: interleaving of packets within a VC, VC occupancy across several flits, and tail-triggered release. Credits stay per flit, so the flow-control argument carries over; VC allocation moves to the head flit and must no longer be assumed to follow switch allocation.
  2. Faster allocation. The data states the target: for the two-pass VC router to beat the pipelined 1 VC × 8 router per nanosecond it needs a clock under about 4.4 ns, roughly half of today's 7.94 ns. Three known routes: speculative switch allocation in parallel with VC allocation, allocation split across two cycles with replay of stale nominations, and a wavefront allocator giving a maximal matching in one pass.
  3. Physical implementation. Place and route on sky130 to replace pre-layout estimates, add wire delay to the cross-link path, and measure power. Expect the pipelined designs to gain, since their second stage has slack.
  4. Rate limiting and a wider threat model. A token bucket at the local port closes the flooding gap. A second compromised tile or colluding tiles would test whether per-port defenses still compose.
  5. Stronger formal results. Unbounded proofs of the credit protocol by induction with supporting invariants; a temporal proof of protocol deadlock freedom on an abstract model of the network.
  6. Workload realism. Trace-driven runs from a coherence simulator; other traffic mixes; adaptive routing studies.

Appendix EToolchain notes and simulator quirks

E.1  Icarus Verilog 12.0 (devel) constructs avoided

These are the places this build crashes, warns or silently misbehaves. The RTL and testbenches are written around each; the same sources lint cleanly in Verilator and synthesize in Yosys.

ConstructSymptom and workaround
A for loop reading a packed-struct field inside always_combCompiles with a cosmetic warning, then corrupts the simulation (vvp crashes a few edges in). Use generate loops.
Comparing two loop-indexed array reads in a nested procedural loopSame failure mode. Use generate loops.
An output port declared as an unpacked array of a packed struct, written in a generate blockReads as x from outside the module. Declare it as a packed array.
Concurrent assertions (property, assert property)Not parsed. Use immediate assertions and procedural bounded-wait counters; prove the temporal versions formally in M7.
Package functions called inside generate blocks after import noc_pkg::*Not found. Call as noc_pkg::vn_of(...).
int arrays connected through continuous assignsCrash vvp at run time. Use logic arrays in testbenches.
$display inside always_ffFloods -Wall with "cannot be synthesized". Simulation-only checkers are plain always blocks.
Writing a constant-indexed unpacked-array element inside always_combWarns once per instance. The routing function is a continuous-assign ternary chain.
Package import in the module headerCrashes the compiler. Import at file scope, and waive Verilator's IMPORTSTAR.
A signal named beforeIt is a SystemVerilog keyword. Renamed.
Chained unpacked arrays in an encoderVerilator reports a false combinational loop (UNOPTFLAT). Use flat one-hot-to-binary encoders.

E.2  Environment notes

  • vvp exits 0 even when a testbench prints FAIL; scripts must match the pass line.
  • A full-mesh VCD is about 19 MB per run, so batch sweeps pass +NODUMP; run a single point by hand to get its waveform.
  • SymbiYosys file lists cannot contain spaces: use relative paths from each proof's directory. It exits non-zero on an expected FAIL, so scripts read the verdict from the last DONE line.
  • Verilator's Perl wrapper fails under Git Bash; call the executable directly.
  • Running eight Yosys jobs in parallel can crash on memory; use three or four with a retry.
  • Python on Windows writes carriage returns in text mode; open files with newline='' when scripts edit sources that shell tools read.
  • The sky130 liberty file comes from OpenROAD-flow-scripts. Cells prefixed lpflow_ are excluded from mapping.
