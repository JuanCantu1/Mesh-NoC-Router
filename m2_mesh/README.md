# M2 -- Full Mesh

A 3x3 grid of M1 routers, wired together into a real mesh, with a directed
testbench proving XY routing composes correctly across multiple hops --
straight lines, corner-to-corner turns, independent concurrent traffic, and
cross-router arbitration.

See [NoC Router 101](../README.md) for a from-scratch explanation of the
concepts this milestone builds on (packets, XY routing, arbitration,
handshakes) if you haven't read M1's docs yet -- this document assumes them.

## What's new versus M1

M1 built and verified **one** router in isolation. This milestone doesn't
change the router at all (`rtl/router.sv`, `rtl/rr_arbiter.sv`,
`rtl/noc_pkg.sv` are untouched copies of M1's files) -- it adds exactly one
new module, `rtl/mesh.sv`, that instantiates a grid of them and wires every
router's N/S/E/W port to its actual neighbor's opposite port.

## Block diagram

```
                 X=0        X=1        X=2
              +--------+ +--------+ +--------+
     Y=0      | router | | router | | router |
              | (0,0)  |-| (1,0)  |-| (2,0)  |
              +--------+ +--------+ +--------+
                  |          |          |
              +--------+ +--------+ +--------+
     Y=1      | router |-| router |-| router |
              | (0,1)  |-| (1,1)  |-| (2,1)  |
              +--------+ +--------+ +--------+
                  |          |          |
              +--------+ +--------+ +--------+
     Y=2      | router |-| router |-| router |
              | (0,2)  |-| (1,2)  |-| (2,2)  |
              +--------+ +--------+ +--------+

  Every router also has a Local port (not drawn) exposed at the mesh
  boundary as local_in_*/local_out_*[TILE], TILE = Y*MESH_W + X.
```

Edge-facing ports (e.g. router (0,0)'s North and West) have no neighbor,
so `mesh.sv` ties them off: their inputs are permanently not-valid, and
their outputs are permanently ready (never expected to actually be used,
since XY routing never tries to leave the grid for an in-range destination).

## Important: this mesh has no per-hop latency yet, and that's expected

M1's router is **purely combinational** end to end -- there is no register
anywhere between an input port and an output port, other than the
round-robin arbiter's internal pointer. Wiring routers directly together,
as `mesh.sv` does, means there is *still* no register between one router's
output and the next router's input. The practical consequence, confirmed
by this milestone's own testbench: a packet injected at one corner of the
3x3 grid and destined for the opposite corner (4 hops away) arrives **in
the same clock cycle it was injected**, as long as nothing contends with
it along the way.

This is not a bug, and it's not something to "fix" in this milestone -- it's
the direct, expected consequence of M1's explicitly scoped-down design
("Simple valid/ready handshake per port (no credits/VCs yet)"), and it's
exactly what M3 exists to change. Two things are true at once:

- **Functionally**, this is fine to verify right now: XY routing's
  *decisions* (which output port, hop by hop) are what M2 needs to prove
  correct, and they are, regardless of how many clock edges they take.
- **Physically**, this would never meet timing in real silicon: the
  combinational path length grows with the mesh's diameter, so a bigger
  mesh means a longer, slower critical path with no way to pipeline it.
  Real NoC routers register at least their outputs (often their inputs
  too) for exactly this reason.

M3 (credit-based flow control) naturally fixes this as a side effect of
adding real per-hop buffering: once each router has an input buffer with
its own registered state, a hop takes a real, bounded clock cycle, and the
combinational path per hop is bounded to one router's logic no matter how
large the mesh gets.

## Files

```
m2_mesh/
  rtl/
    noc_pkg.sv     -- unchanged copy of M1's shared types/params
    rr_arbiter.sv  -- unchanged copy of M1's round-robin arbiter
    router.sv      -- unchanged copy of M1's 5-port router
    mesh.sv         -- NEW: wires an MESH_W x MESH_H grid of routers together
  tb/
    mesh_tb.sv      -- NEW: self-checking directed multi-hop testbench
  sim/              -- build output (.vvp, .vcd) -- gitignored, regenerated by run.sh
  run.sh            -- compiles + runs everything with Icarus Verilog
```

## How to run it

```sh
./run.sh
```

or manually:

```sh
iverilog -g2012 -Wall -o sim/mesh_tb.vvp rtl/noc_pkg.sv rtl/rr_arbiter.sv rtl/router.sv rtl/mesh.sv tb/mesh_tb.sv
vvp sim/mesh_tb.vvp
```

## What's verified

| Scenario | Path | Proves |
|---|---|---|
| Adjacent hop | (0,0) &rarr; (1,0) | The mesh-level wiring between two neighbors is correct |
| Straight row | (0,1) &rarr; (2,1) | Two hops in X with no turn, across a shared row |
| Straight column | (1,0) &rarr; (1,2) | Two hops in Y with no turn, across a shared column |
| Corner to corner | (0,0) &rarr; (2,2) | A full 4-hop path with a turn (2 east, then 2 south) |
| Corner to corner (other diagonal) | (2,0) &rarr; (0,2) | Same, routing West-then-South instead of East-then-South |
| Concurrent independent traffic | (0,0)&rarr;(2,0) *and* (0,2)&rarr;(2,2) at once | Two packets on paths that share no router don't interfere |
| Cross-router contention | (1,0)&rarr;(2,0) *and* (0,0)&rarr;(2,0) at once | The same round-robin arbiter M1 verified locally also resolves contention where the requesters arrive from different physical directions (one from Local, one having just hopped in from a neighbor) |

**Not yet covered (future milestones):** any actual per-hop latency or
buffering (M3), randomized/stress traffic and a throughput sweep (M4),
mesh sizes other than 3x3 (trivial to parameterize -- `mesh.sv` already
takes `MESH_W`/`MESH_H` -- just not exercised by this milestone's
testbench yet).
